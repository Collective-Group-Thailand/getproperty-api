## 1. Platform-unique verified slip reference (D-308)
- `ops.slip_review`: the per-tenant `UQ (tenant_id, trans_ref)` becomes **`UQ (trans_ref)` across tenants** for rows not `duplicate` / `rejected` (a unique index is enforced whatever RLS hides). The migration refuses to run when two tenants already hold the same live reference (it never rewrites a booked slip; resolve by hand — `docs/deployment.md`).
- `ops.slip_trans_ref_holder(ref, slip_id, tenant_id) → 'none' | 'same_tenant' | 'other_tenant'` — `SECURITY DEFINER` (owner = migration role), granted to `gp_app` / `gp_platform`: tells **only** whether the reference is used and by whom relative to the caller; never the other tenant, building or slip.
- Worker verify: `other_tenant` → the slip is `rejected` at once (reason `duplicate_reference_platform`, `reject_reason` = `payment.duplicate_slip`), event `slip.duplicate_rejected` → resident notice; `same_tenant` keeps today's behaviour (`duplicate`, owner queue). Owner approve of a slip whose reference became used elsewhere → **409 `payment.duplicate_slip`**; a race on the unique index maps to the same 409.
- New **date window** (`payments.slip_max_age_days`, 30; platform / tenant): a slip dated more than N days before the upload or more than 1 day after it → reason `date_out_of_window` (owner review). Receiver account and amount checks unchanged.

## 2. Allocation policy, partial payments, overpayment credit
- Setting `payments.allocation_policy` (platform / tenant): `oldest_first` (default; today's behaviour) · `surcharge_first`.
- Pure allocator `engine/allocation.ts` `planAllocation(amount, targets[], policy)`; targets = any set of open invoices (one unit today; one owner's units for the J1.2b statement) with `balance` and `surchargeOpen` (Σ `late_fee` lines − surcharge already allocated − credited surcharge, ≤ balance). `oldest_first`: invoices by issue date; inside an invoice its surcharge first. `surcharge_first`: pass 1 every invoice's open surcharge (oldest first), pass 2 the principal (oldest first). The rest = payer credit (existing `ops.payer_credit`, used by the next invoice on issue).
- `ops.payment_allocation.surcharge_amount` records the surcharge part (CK 0 ≤ … ≤ amount).
- Partial payments stay behind `payments.allow_partial` (D-044; juristic tenants switch it on).
- **Manual channel for juristic tenants**: cash and hand-recorded transfers need an attachment (`evidenceDocumentId`) **and** a note (≥ 5 chars, e.g. a foreign transfer's sender bank / SWIFT ref) → 422 otherwise. Apartments unchanged.

## 3. Payment plans (§7.6 J1-n / J1-o)
- `juristic.payment_plan` (proposed → active → completed · defaulted · cancelled; proposed → rejected · cancelled) and `juristic.payment_plan_instalment` (scheduled → billed → paid · cancelled).
- Staff proposes (`POST /v1/owner/juristic/payment-plans`) or the resident requests (`POST /v1/resident/units/{unitId}/payment-plan-requests`); one open plan per party × unit (`payment_plan.open_exists`); 2…`juristic.plan_max_instalments` (12) monthly instalments from `firstDueOn` (default the 1st of next month).
- Approval (`…/actions/approve`, permission `juristic.payment_plan.approve` = owner, manager, committee; `Idempotency-Key`): principal = Σ balances of the party's open invoices of the unit **at approval**; each covered invoice gets a credit note for its balance (reason `payment_plan`) — the debt moves onto the plan, never lost; instalments = principal ÷ n half-up, the remainder on the last (Σ exact); `default_after_days` snapshot of `juristic.plan_default_days` (30). Event `juristic.payment_plan.approved`.
- Job `payment-plans` (hourly): an instalment's charge (line kind `plan_instalment`, source `adjustment`) is queued on the first day of its due month → billed by the next monthly cycle; billed instalments become `paid` when their invoice is paid; the plan completes when all are paid. **Default**: a billed instalment whose invoice is still unpaid more than `default_after_days` after its due date → plan `defaulted`, future instalments cancelled, the unbilled rest of the principal queued as one charge (acceleration = the original debt, never a penalty), event `juristic.payment_plan.defaulted` (J1.2b ladder resumes).
- Cancel (`…/actions/cancel`, reason): proposed → cancelled; active → cancelled with the same acceleration. Reject (proposed). Resident withdraw (own proposed request).

## 4. Recurring channel (D-308, O-020)
- `ops.payment_method` + `recurring`; `ops.payment_mandate` (pending → active → revoked · failed; scope `advance_invoices` (default) · `all_invoices`), `ops.recurring_charge`, `ops.recurring_webhook` (platform-only, UQ provider × event id).
- Port `RECURRING_PAYMENTS` (`src/integrations/recurring-payments/`): `FakeRecurringPayments` (in-memory mandates / charges, HMAC-SHA256 signed callbacks with `RECURRING_WEBHOOK_SECRET` or the fake default) and `UnconfiguredRecurringPayments` (O-020: `recurring.unavailable`); `RECURRING_PAYMENTS_MODE` `fake | off` (default fake with fakes, else off). No real adapter until O-020.
- Resident: `POST|GET /v1/resident/units/{unitId}/payment-mandates`, `POST …/{mandateId}/actions/cancel`. Owner: `GET /v1/owner/payment-mandates`, `POST …/{id}/actions/revoke`.
- `POST /webhooks/recurring/{provider}` (signed `X-Recurring-Signature`, idempotent per event id; replay → `duplicate: true`): `mandate.activated|failed|revoked`, `charge.succeeded|failed`.
- On `invoice.payment_ready` (after the payer's credit): an invoice of an **advance cycle** (quarterly / semiannual / annual; every invoice with scope `all_invoices`) with an active mandate of the billed party × unit and a balance is charged once (`recurring_charge` pending); `charge.succeeded` books a `recurring` payment through the allocator (receipt as usual).

## 5. Debt clearance (D-306, §7.6 J1-p)
- `juristic.debt_clearance` (requested → issued · refused); `ops.document_type` + `debt_clearance` (series **`DCL`**, gapless); core document kind `pdf_certificate`.
- Outstanding for the requesting owner on `asOf` (today … +60 days) = Σ balances of issued invoices of the unit billed to the owner or the owner's bill-to payers + pending one-off charges / surcharges / instalments queued up to `asOf` + drafts whose period starts on or before `asOf` − the owner's credit on the unit (never below 0).
- `POST /v1/resident/units/{unitId}/debt-clearance-requests` (co-owner only) and `POST /v1/owner/juristic/debt-clearances` (`Idempotency-Key`): outstanding > 0 → **409 `debt_clearance.outstanding`** (`params.amount`, nothing stored); 0 and fee 0 → issued at once (PDF via the document pipeline, verification code + QR to `<web>/verify/<code>`, `valid_until` = issue + `juristic.debt_clearance.validity_days` (30)); fee > 0 (`juristic.debt_clearance.fee`, default 0.00) → `requested` + a one-off fee charge, issued by the owner (`…/actions/issue`, re-checked) once paid. Owner list / get / refuse (reason) / document; resident list / document.
- `GET /v1/public/documents/verify/{code}` (new): document type, number, status (`valid` · `expired` · `refused`), issued / valid until, issuer (tenant display name), unit number, holder **initials only** (PDPA); unknown code 404.
