## 1. Shape
- One **import job per building** (§7.6 J3-a: `bld`) of a building the juristic tenant operates or owns, with an
  **as-of date** (the legacy cut-off; Bangkok date ≤ today). Several towers = several jobs. The building itself is
  created by the onboarding (it needs `legal_form`, D-324 (1)); the wizard **attaches** to it and creates floors /
  sois, units, parties, ownerships and bill-to (the pack's "create/attach properties/buildings" → attach; recorded).
- Up to five **sheets** per job (deviation from §7.6's one `kind` per job — cross-file checks and one commit need them
  together): `register` (required), `opening_balance` (required, may be empty of arrears), `payment_history`
  (optional), `bank_balance` (optional), `legacy_bills` (parallel cycle only, after commit).
- Files: CSV (UTF-8, BOM optional, `,` or `;`) or XLSX (exceljs, already a dependency), ≤ 5 MB, ≤ 5,000 rows; uploaded
  through `files/presign` (`fileId`, kind `other`) **or** inline base64 (`fileName` + `content`, stored as a
  `core.document` kind `other`). Headers: the column key, the Thai label, the English label or `label (key)` — the
  templates write `ป้ายไทย (key)` / `English label (key)`.
- States: `draft` → `validated` (every required sheet present, no row errors) → `reconciled` → `committed` → `live`;
  `rolled_back` (from committed), `cancelled` (before commit). An upload / removal moves the job back to `draft` and
  clears the reconciliation.

## 2. Templates (`GET …/imports/templates/{sheet}?format=xlsx|csv&language=th|en`)
XLSX: data sheet (header row, two example rows marked `#` in the first column are ignored), instructions sheet
(column, meaning, required, format, rules) in the chosen language. CSV: header row + examples.
1. **register** — `building` (optional check against the job's building), `floor` (floor level number or soi / zone
   name), `unit_no`*, `unit_type` (condo_unit · house · plot · shop · parking; default by building type), `plot_no`,
   `land_area_sqwa`, `area_sqm`, `ownership_ratio` (0–1, 6 dp, `core.unit.ownership_ratio`), `owner_code` (legacy id; the key the other sheets use; default name + phone),
   `owner_name`*, `owner_type` (person · company), `id_type` (thai_national_id · passport · other), `id_last4`
   (exactly 4 characters — **a longer value is refused and never stored**, PDPA), `phone`, `email`, `line_id`
   (optional, kept only on the import row — a LINE id is linked by the resident's own login, D-322), `share_pct`
   (default 100 / owners of the unit), `owned_since` (default the as-of date), `bill_to_name`, `bill_to_kind`
   (named_party · agency), `bill_to_phone`, `bill_to_email`. One row per unit × owner.
2. **opening_balance** — `unit_no`*, `owner_code` / `owner_name` (must be an owner of that unit in the register),
   `charge` (common_fee · fund; default common_fee), `period`* (`YYYY-MM`, `YYYY-Qn`, `YYYY-Hn`, `YYYY`; must end on
   or before the as-of date), `principal`, `surcharge` (≥ 0, one > 0), `as_of` (optional; = the job's).
3. **payment_history** — `unit_no`*, `owner_code`/`owner_name`, `paid_on`* (≤ as-of, ≥ as-of − 366 days), `amount`*,
   `method` (cash · transfer · cheque · promptpay · card · other), `reference`.
4. **bank_balance** — `account_type`* (operating · fund), `bank_account_last4` (a tenant bank account whose masked
   number ends with it), `fund_name` (a fund of the building; blank = the building's default fund), `balance`* (≥ 0),
   `as_of` (= the job's).
5. **legacy_bills** — `unit_no`*, `amount`* (Σ per unit of what the legacy system billed for the compared cycle).

## 3. Validation (per row, per column; messages th / en by `language`)
Required / format / range per column; duplicates (unit × owner; unit × owner × charge × period; bank rows); Σ shares
per unit ≤ 100 (error) and < 100 flagged `incomplete` (warning, like the register); a unit that already exists keeps
its attributes (a different value → warning) and must have **no current owners** (error — the register would double);
a party is **attached** when the tenant already has one with the same name and the same phone or e-mail, else created;
cross-file: an opening-balance / history row must name a unit of the register and an owner of that unit; bank rows need
a matching bank account (exactly one) / fund. Errors and warnings are stored on `juristic.import_row` as
`{column, code, params}`; the row's data is stored **normalised** (ID: type + last 4 only). Preview
(`GET …/{id}/preview`): units new / attached, floors new, parties new / attached, ownerships, incomplete units,
bill-to, opening invoices (count, Σ principal, Σ surcharge, units in arrears), history (count, Σ), bank (Σ operating, Σ
fund). Bad rows: `GET …/{id}/bad-rows?sheet=&format=csv|xlsx&language=` = the sheet's rows with errors and an
`errors` column, ready to fix and re-upload.

## 4. Reconcile (`POST …/{id}/actions/reconcile`)
Body: `declaredReceivables` (the legacy system's total), optional `note` + `documentId`. Items: **receivables**
(Σ principal + surcharge of the sheet vs declared) and one item per **bank row** (declared opening balance vs the
balance of the last J2.1 statement line with a balance on or before the as-of date of that bank account — the fund's
bank account for fund rows; none → `no_statement`). Any item not `match` → commit needs the explanation: `note`
(10–2000) **and** an attachment (`documentId`, a document of the tenant) — stored on the job as `reconciliation`
(items), `reconciliation_note`, `reconciliation_document_id` (422 `import.reconciliation_unexplained` otherwise).

## 5. Commit (`POST …/{id}/actions/commit`, Idempotency-Key, one transaction)
Re-validates against the database (409 `import.stale` when the plan changed — e.g. a unit created meanwhile), then:
floors, units (`UnitsService.insertUnit`, source `import`; no tenant-party ownership for juristic tenants), parties
(new ones; events `party.changed`), ownerships (source `import`), bill-to (the job's `billToConsentDocumentId` is
**required** when the register names any bill-to — 422 `import.bill_to_consent_required`: one scan of the signed
consents covers the batch), **opening-balance invoices** as **drafts** (one per unit × billed party — the owner or the
owner's bill-to, D-324 (4) — period = first period start … as-of; lines: one `opening_balance` line per charge ×
period (source type `common_fee` / `fund`) + one `late_fee` line (source `penalty`, "เงินเพิ่มยกมา") per period with a
surcharge, so the allocation policy and the surcharge rule (never a surcharge on a surcharge) treat it as surcharge;
`ops.invoice.import_job_id`, review flag `opening_balance_pending_go_live` — not issuable), **payment history as
history only** (`juristic.legacy_payment`): the legacy balance already nets them; turning them into payments would
issue receipts for money the legacy system received and double the bank opening balance. Every created id is recorded
in `juristic.import_created` (entity, id, seq). Audit `juristic.import.committed`, event `juristic.import.committed`.
**No journals before go-live** (the GL is immutable, D-329; a rollback must leave nothing).

While a building has a committed job that is not live, **no invoice of that building can be issued** (409
`import.go_live_pending`): the legacy system still bills during the parallel cycle; double billing and notifications
are impossible; no invoice → no overdue → no ladder (D-326).

## 6. Rollback (`POST …/{id}/actions/rollback`, Idempotency-Key, reason) — committed only
Deletes, newest first, exactly the rows in `import_created` (+ the drafts computed meanwhile for the job's units or
parties — derived, recomputable). Anything else referencing them (a payment, an issued document, a lease, a slip…) →
409 `import.rollback_blocked` with the blocking table; nothing is deleted. State `rolled_back`; audit + event.

## 7. Parallel cycle (`POST …/{id}/parallel-cycle`, `GET …`, explain a difference)
After commit: a billing cycle of the building's property (opened / computed by the existing cycle endpoints) and the
`legacy_bills` file → per unit: computed (Σ non-void invoice totals of the cycle for the unit) vs legacy → rows in
`juristic.import_cycle_difference` (replaced on each run). A difference ≠ 0 needs an explanation (reason 5–1000).
Go-live: settings `juristic.import.parallel_cycle_required` (default **true**: D-313 asks for one parallel cycle) and
`juristic.import.allow_unexplained_differences` (default **false**; when true, go-live needs
`acknowledgeDifferences: true`, recorded).

## 8. Go-live (`POST …/{id}/actions/go-live`, Idempotency-Key) — committed only
In one transaction: opening drafts lose their flag and are issued (`InvoicesService.issueInTx`, number series
**`OPB`** = new `ops.document_type` `opening_balance`; due date by the normal rules — the opening balance is noticed
in the new system with the usual lead time, the ladder runs from that due date); `notifyOpeningBalances` (default
true) — false sends them silently (`notify: false` in the event payload; the LINE / e-mail resolver skips them);
bank opening journals (`source_type opening`, one per bank row: Dr the bank account's GL account / Cr accumulated
surplus; fund rows Dr fund bank / Cr fund equity of the fund); ledger rule: `opening_balance` lines → accumulated
surplus (fund lines → fund equity), opening `late_fee` lines → accumulated surplus. State `live`, `rollback_until`
closed. From now on the building issues normally; the ladder opens cases on the first overdue opening invoice.

## 9. Full export (`POST /v1/owner/juristic/export`) — "you can leave any time"
Export job kind `juristic_full_export` (worker): a ZIP with one CSV per table — **every `juristic.*` table** (found in
the catalogue, so later tables are included automatically) and the tenant's `ops` billing tables (invoice,
invoice_line, invoice_charge, credit / debit notes + lines, payment, payment_allocation, receipt, billing_cycle,
rate_plan, rate_plan_version) and `core` register (property, building, floor, unit, party, unit_ownership,
occupancy) filtered by `tenant_id`; `bytea` columns (encrypted ID numbers, hashes) are left out; a `manifest.csv`
lists table, rows, columns. Permission `juristic.export.run` (owner, manager).

## 10. RBAC, menu, settings, retention
`juristic.import.read` (owner, manager, committee, auditor) · `juristic.import.manage` (owner, manager) ·
`juristic.export.run` (owner, manager). Menu `juristic_import`. Job **`juristic-imports`** (daily): import rows of
jobs live / rolled back / cancelled more than 90 days ago are deleted (§7.6 J3-b); the files keep their document
retention (class `other`, ≥ 1 year).
