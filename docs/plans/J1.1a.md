# J1.1a — Co-owner shares, transfer proration, owner sweep, billing frequency (plan + record)

Step **J1.1a** of `docs/prompts/J-juristic-api.md` (pack J, D-303 = D-J02, D-307 = D-J06), the first half of J1.1 as split by the team lead after J0 (`docs/juristic-gap.md` §7 item 3). Branch `feat/J1.1a-billing-shares-frequency` from `main` `c66e284` (asset-core 0.8.0). J1.1b keeps: register / transfer API and the `unit_ownership.transferred` event, bill-to, `per_sqwa` / `budget_split` bases, budgets / resolutions, credit notes for a transfer after an advance invoice was issued (`juristic.transfer_proration`).

## What is wrong today (J0 findings, re-verified on `c66e284`)
1. **Co-owners each billed the whole fee** — `BillingCyclesService.billables` adds one ownership billable per (unit, party) and the engine charges `ratio × budget` per billable; `share_pct` is never read (`billing-cycles.service.ts:304-325`, `engine/invoice-draft.ts` step 5).
2. **An ownership change inside the period bills seller and buyer in full** — an ownership billable has no lease, so its occupancy is the whole period (`:541-546`). In addition the period filter is `valid_to ≥ period_start` although `core.unit_ownership.valid_to` is **exclusive** (`daterange(valid_from, valid_to)`, `[)`), so an owner whose row ended on the first day of the period was billed the whole period too.
3. **The sweep opens a cycle only where a lease lives** (`:861-866`): a condominium with owners and no leases never gets an automatic cycle.
4. **Monthly only** — `smart-readings/cutoff.ts`, the cycle keys `UQ (property_id, period_key)` / `UQ (property_id, period_start)`, the DTO `periodKey` pattern, `previousPeriodKey`.

## Golden cases first (`test/unit/billing-juristic.golden.spec.ts`, files in `test/golden/billing/`)

## Design
### Engine (pure)
- `engine/ownership-shares.ts` `allocateByOwnership(periodAmount, period, rows)` → slices per party: the period is cut at every ownership start / end (end exclusive); each segment's amount = `round(P × cumEnd / N) − round(P × cumStart / N)` (cumulative half-up rounding, so seller + buyer = P exactly); inside a segment each owner gets `round(segment × share / 100)` half-up and the remainder goes to the largest share (ties: first by party id); consecutive slices of one party with the same share merge. Σ shares < 100 on a day → flag `ownership_shares_incomplete` (review flag: the draft is not issuable until the register is complete — never bill an owner more than their share).
- `DraftInput.ownership?: { partyId, rows[] }` — when present, step 5 emits the billed party's slices (one line per slice, tier part `ownership_share`, description with share and days); without it the old path is unchanged (existing goldens).
- `DraftInput.cycleMonths?: number` (1, 3, 6, 12) — rate amounts stay **per month** (`unit: month`, D-151 meaning unchanged); the period amount is `monthly exact × months`, rounded once. Budget tiers gain `period: 'month' | 'year'` (`year` → amount ÷ 12 per month).
- `engine/revenue-schedule.ts` `monthlySchedule(amount, from, to)` → one row per calendar month by calendar days, cumulative rounding (Σ = amount).
### Periods (`smart-readings/cutoff.ts`)
- `parsePeriodKey` / `frequencyOfKey`: `YYYY-MM` monthly · `YYYY-Qn` quarterly · `YYYY-Hn` semiannual · `YYYY` annual. Monthly bounds unchanged (cut-off of `billing.cutoff`). Non-monthly periods are **calendar-aligned** (1 Jan / 1 Apr / 1 Jul / 1 Oct …, Bangkok) and billed **in advance**: the cycle's `cut_off_at` = start of its first day minus `billing.advance_open_days` (new setting, default 0); `periodKeyFor(frequency, date)`, `monthsOf(frequency)`.
### Data (migration **0070**)
- enum `ops.billing_frequency (monthly, quarterly, semiannual, annual)`; `ops.billing_cycle.frequency` NOT NULL default monthly; the two unique keys become **`UQ (property_id, frequency, period_key)`** and **`UQ (property_id, frequency, period_start)`**; CHECK the key format matches the frequency.
- `ops.rate_plan.frequency` NOT NULL default monthly; CHECK non-monthly only for `common_fee` / `fund` (leases, utilities, rent and services stay monthly).
- `juristic.revenue_schedule` (first table of the `juristic` schema; RLS tenant): `invoice_line_id`, `month` (1st), `amount`, `recognised_at` null; UQ (invoice_line_id, month); written when an invoice of a non-monthly cycle is **issued** (draft lines are recomputed, issued ones are immutable — D-040); J2.1 recognises.
### Service
- **Billables** per cycle frequency: leases only in monthly cycles; ownership billables (juristic tenants) for every unit with an ownership overlapping the period (`valid_from ≤ end`, `valid_to > start`), each carrying all rows of its unit; their unit rate plans are the default `common_fee` / `fund` plans **whose frequency is the cycle's**; an ownership billable without such a plan and without pending charges is skipped.
- Ownership draft period = the party's own span inside the cycle.
- Rate version: monthly as before (in force at period end); advance cycles take the version in force on the period start (else at the end) — a mid-cycle version change applies from the next cycle.
- **Sweep**: per property, monthly as before when the property has a live lease **or** (juristic) a current ownership with a monthly unit plan; plus one advance cycle per non-monthly frequency of the property's default `common_fee` / `fund` plans when ownerships exist, opened when `now ≥ cut_off_at` of the period containing `now + advance_open_days`.
- **Due date** of an advance-cycle invoice: the first `billing.default_due_day` on or after the invoice period start (instead of after its end), never inside `invoice.min_lead_days`.
### API (contract)
- `BillingCycleDto.frequency`; `BillingCycleOpenDto.periodKey` accepts the four formats (frequency from the key; default current monthly period); list filter `frequency`.
- `RatePlanDto.frequency`; `RatePlanCreateDto.frequency` / `RatePlanUpdateDto.frequency` (422 `rate_plan.frequency_not_allowed` style field error for other kinds).
- Budget tier `period: 'month' | 'year'` documented.
- `GET /v1/owner/invoices/{id}` lines already expose `tierBreakdown` (share part) — no new field.
