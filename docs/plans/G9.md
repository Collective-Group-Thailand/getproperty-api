## 1. Verified reviews (E13; schema G9-a → §7.5 rows 195–196)
- `ops.building_review` (+ enum `ops.building_review_state` pending_moderation | published | rejected | hidden |
  withdrawn): tenant (= the lease's tenant), building, unit, `lease_id` **UQ** (one per lease), `author_party_id`,
  `author_user_id` (withdrawal / DSR; never returned), rating 1–5, body ≤ 2000 (NULL once withdrawn), language,
  `tenure_from` / `tenure_to` (dates; shown as months), `consent_id` (purpose `review.publish`), moderation fields,
  `owner_reply` ≤ 1000 + replied at / by, owner report (`reported_at`, `report_reason`), version. RLS tenant;
  **no DELETE grant + trigger refusing DELETE** (owner can never delete); immutable author / lease / rating / tenure
  after insert; withdrawal erases the body.
- **Verified tenure only** (LIFF GL4): the reviewer is a lessee / co-tenant / occupant of the lease (not a guarantor)
  linked to the login; the lease was activated; eligible **after move-out** (ended / terminated, within
  `review.window_after_end_days` 365) **or after `review.min_tenure_months` (3)** of tenure (move-in or start date).
  Otherwise `review.not_eligible` (409, with `eligibleFrom`).
- Consent: purpose **`review.publish`** (resident, optional, controller Collective → tenant NULL) granted explicitly with
  the review (`consentVersion` = current version, else `review.consent_required`).
- Screening (pure `review-rules.ts`): bank account numbers (D-267 message safety), phone numbers, e-mail addresses, LINE
  ids, links and Thai ID-like numbers are refused (`review.personal_data`, 422) — protects the reviewer and others.
- Moderation: `review.moderation.premoderate` (default **true**, conservative — defamation risk, O-035): a review waits
  in `pending_moderation` until a platform moderator approves (→ published) or rejects (reason); false = published at
  once. Published reviews may be hidden for abuse (reason) and restored by the platform (`admin.listing.moderate`).
  The owner may **report** a review (reason) — it goes to the platform queue; the owner **cannot hide or delete**.
- Right of reply: the owner (listing.manage) writes / edits one public reply (screened the same way).
- Public: `GET /v1/public/listings/{slug}/reviews` — the listing's building: count, average, distribution, published
  reviews with rating, body, tenure months (YYYY-MM), "verified tenant" label, owner reply. **No name, party, unit
  number or exact dates** of the reviewer.
- Resident: `GET /v1/resident/leases/{leaseId}/review` (eligibility + my review + consent text), `POST` (Idempotency-Key),
  `POST …/review/actions/withdraw` (body erased). Owner: `GET /v1/owner/reviews`, `GET …/{id}`, `PUT …/{id}/reply`,
  `POST …/{id}/actions/report`. Admin: `GET /v1/admin/reviews`, `POST …/{id}/actions/approve|reject|hide|restore`.
- DSR: export includes the person's reviews; erasure withdraws them (body erased; rating aggregate drops).

## 2. Listing assistant (E15; G9-b → row 197)
- `platform.ai_feature` + `listing_assistant`.
- Local port `LISTING_WRITER` (`src/integrations/listing-writer/`): `FakeListingWriter` (deterministic template text from
  the facts, dev / tests) and `HttpListingWriter` (Collective AI gateway, assumed `POST {AI_GATEWAY_URL}/v1/vision` with
  the shape of the shared vision adapter, purpose `listing_assistant`, model `AI_TEXT_MODEL`; **// UNVERIFIED**);
  real mode without URL / key → `ai.unavailable` (503).
- `POST /v1/owner/listings/{listingId}/assistant` (Idempotency-Key, listing.manage): languages ⊆ th / en / zh, optional
  `includePhotos` (≤ `listing.assistant.max_photos` (3) cover photos are **read** and sent; the assistant returns text
  only — photos are never changed, re-encoded or re-stored). Facts = the listing's own fields (no tenant / party data).
  Returns title + description per language, the model and the disclaimer; nothing is written to the listing (the owner
  edits and saves through the existing PATCH). Each call writes one `platform.ai_usage_record` (feature
  `listing_assistant`, tokens, subject the listing), errors too (outcome `error`). Limit per tenant per Bangkok month:
  `listing.assistant.monthly_limit` (30) → `ai.limit_reached` (429); `listing.assistant.enabled` (true).
- Output is checked: non-empty, ≤ the listing field limits, no bank account / phone / link (stripped → refused as
  `ai.output_rejected` 502 and recorded as error).

## 3. Energy insight → getenergy (E15; G9-c → rows 198–200)
- Score (pure `energy-score.ts`, model in setting `energy.insight.score_model`): from `smart.telemetry_1h` electric
  meters of the building over the last `energy.insight.window_days` (30) full Bangkok days — total kWh, common-area kWh
  and share, peak hourly demand (kW), load factor, pump hours per day (common-area meters labelled pump / ปั๊ม), data
  days (main meters are the total when they report, else unit + common-area meters). Fewer than `energy.insight.min_days` (14) → no score (`insufficient_data`).
  Score 0–100 = 100 − weighted penalties (thresholds in the setting).
- `platform.energy_insight_optin` (+ enum `opted_in | opted_out`): tenant, building **UQ**, state, opted in / out at /
  by, `consent_id` (purpose **`energy.insight`**, audience owner, tenant-scoped consent row of the user), last shared at
  / score, version. RLS tenant. Only the building's **owner tenant** may opt in / out (`tenant.settings.update`); its
  operator may read the score (`report.read`).
- `bridge.integration_platform` + `getenergy`; event-type CHECK + `energy.insight.shared`, `energy.insight.withdrawn`.
  **Local provisional contract** (`getenergy-contract.ts`, built with asset-core's `eventEnvelope`) until asset-core
  carries it (O-028) — `IntegrationEventsService.outbound` validates getenergy events against it.
- Payload = aggregate / anonymised only: lead id (opt-in id), building ref, province / district, tenant type, unit-count
  band, window, score, metrics. **No names, contacts, unit numbers, resident or per-unit data** (contact sharing waits for
  O-036 / the shared PII key).
- Flow: opt-in (Idempotency-Key, explicit `consentVersion`) → consent row + opt-in row + domain event
  `energy_insight.opted_in` (outbox) → subscriber computes the score and writes `energy.insight.shared` into
  `bridge.integration_event` **only while opted in** (no score → nothing sent). Job `energy-insight` (daily) shares a
  fresh snapshot every `energy.insight.share_every_days` (30). Opt-out → consent withdrawn, pending getenergy events of
  the building parked (`dead`, "opted out"), `energy.insight.withdrawn` sent so getenergy deletes the lead.
- Transport: `INTEGRATION_GETENERGY_TRANSPORT` = `none` | `webhook` (signed by `signIntegrationWebhook`) | `fake`
  (in-memory, records); unset → `fake` with the fakes, else `none` (events wait, O-028). Delivery job unchanged.
- Owner: `GET /v1/owner/buildings/{buildingId}/energy-insight` (score, metrics, opt-in state, consent text),
  `POST …/energy-insight/actions/opt-in` (Idempotency-Key), `POST …/actions/opt-out`.
