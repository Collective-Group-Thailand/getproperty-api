## 1. Intake (inbound, D-238 receiver)
- `building.handover.requested` (v1 or v2) arrives on the signed `POST /webhooks/integration/getbuild` (fake transport in
  tests; `GETBUILD_MODE` / O-033 unchanged). The receiver already dedups per idempotency key; the consumer stores **one
  `juristic.handover` per integration event** (UQ `integration_event_id`).
- Minimisation (D-025, as D-299): the party envelopes (`phone`, `email` — shared-key ciphertext that getproperty cannot
  open yet) are **dropped**; parties keep `ref`, type, display name, LINE id, language.
- One open handover per developer × building ref: a re-send while one is `received` / `pending_review` **supersedes**
  it (state `superseded`, the new one inherits the assignment); a re-send after an accepted one is refused (the
  integration event is `rejected`, "already handed over"). After a rejection getbuild may send a corrected event.
- Assignment: when a building with `source_ref = getbuild:<buildingRef>` exists and is owned / operated by a juristic
  tenant, the handover is assigned to it at once (`pending_review`); otherwise it waits (`received`) for the platform
  admin: `GET /v1/admin/juristic-handovers`, `POST …/{id}/actions/assign { juristicTenantId, developerTenantId? }`
  (the juristic tenant is created by the admin first — D-324 (1): juristic tenants are never self-created; the
  developer's getproperty presence is a `pm_company` tenant, optional).

## 2. Juristic office inbox (`/v1/owner/juristic/handovers`)
- `GET` list / `GET {id}` (review): payload totals (units, parties, ownerships, Σ advance fees, Σ first fund
  contributions, Σ receivables brought forward, receiving bank account masked + the matched tenant bank account),
  per-unit rows, problems (unit without owner holding money, missing legal form…), party matches (attach / create).
- `POST {id}/actions/accept` (Idempotency-Key; `juristic.handover.manage`; body `legalForm?`, `propertyKind?`,
  `notifyOpeningBalances?` default true): refused before `requestedHandoverAt` (409 `handover.not_due`) and while
  problems exist (422 `handover.invalid`). Applies **in one transaction**:
  1. property (attach by `source_ref`, else create with `kind` = payload / body / derived from the building type) and
     building (attach by `source_ref`, else create): `legal_form` (payload → body → 422), owner = the juristic tenant,
     operator = the developer tenant when assigned (operator period reason `handover`) else the juristic tenant;
     `handed_over_at`, `registration_no`. An attached building keeps its operator (never taken from the juristic).
  2. floors (attach by level), units (attach by unit number — must have no current owner, 409 `handover.unit_owned`;
     else `UnitsService.insertUnit`, `source_ref getbuild:<ref>`), parties (**never duplicated**: attached when the
     tenant already has a party with the same LINE id or `source_ref getbuild:<developer>:<ref>`; else created with the
     LINE id), ownerships (source `getbuild_transfer`), **party links**: a login holding that LINE id is linked now
     (`integration`), later logins are linked by the existing LINE match at sign-in (D-061) — residents keep identity.
  3. finance (v2): **advance common fees** → `ops.payer_credit` kind `handover_advance` per current owner at `asOf` by
     share (remainder to the largest share, ties first party id, D-323) — the credit pays the next juristic invoices
     (D-044) but is **never set off against brought-forward debt** (opening invoices of a handover take no credit);
     **first fund contributions** → the building's sinking fund (J2.1 default fund); **receivables brought forward** →
     opening-balance invoices (J3.1 machinery: line kind `opening_balance`, source `common_fee`, one invoice per unit
     × owner, items split by share) **issued now** in series **OPB** with the **normal due rule** (`issueInTx`
     `docType: opening_balance`; `notifyOpeningBalances`), `ops.invoice.handover_id`; journals (source `handover`, one
     per unit with money): Dr receiving bank (the tenant bank account whose masked number ends with the same 4 digits
     and bank code, else the operating bank role) / Cr receivable per owner for the advance fees; Dr fund bank / Cr fund
     equity for the fund contribution; opening invoices post Dr receivable / Cr accumulated surplus (D-332 rule,
     ⚖ O-043).
  4. **Invariant**: Σ credits = Σ payload advance fees, Σ opening invoices = Σ payload receivables, Σ fund debits =
     Σ payload fund contributions — otherwise 409 `handover.totals_mismatch` and nothing is written.
  5. state `accepted`, audit `juristic.handover_accepted`, event `juristic.handover.accepted`.
- `POST {id}/actions/reject` (Idempotency-Key, reason 5–1000): state `rejected`; the rejection goes back to getbuild
  through the `GETBUILD_HANDOFF` port (`handoverRejected`, fake in tests, `off` waits); job `juristic-handovers`
  (every 10 min) retries undelivered rejections (≤ 10 attempts).
- `POST {id}/actions/juristic-formed` (Idempotency-Key; `formedOn`, `registrationNo?`): records the juristic person's
  formation; with a developer operator the **operator period switches** (developer → juristic, reason
  `juristic_formed`, `BuildingService.changeOperatorInTx`), the developer keeps a `warranty` grant (write) until the
  last building / unit warranty end of the payload when there is one; event `juristic.handover.formed` → subscriber
  writes the outbound `juristic.formed` integration event (asset-core contract; delivered by the D-238 outbox job).
