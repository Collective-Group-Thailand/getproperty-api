## 1. Guard audience and devices (D-320, §7.6 J4-a … J4-c)
- `platform.audience` + **`guard`**; surface `guard` (`/v1/guard/*`, scheme `guardBearer`). The audience guard accepts only guard tokens there; the tenant comes from the token's single `tenant:` scope and the membership is re-checked on every call (role must be `guard`).
- **Gate** `smart.gate` (tenant = the property's tenant, property, name, kind `main | side | service`, state, `barrier` / `lpr` flags for J4.2). Owner `/v1/owner/gates` (create, list, get, patch).
- **Gate tablet** `smart.gate_device` kind `guard_tablet` (`barrier`, `lpr_camera` reserved for J4.2): the owner asks for an **enrolment code** (`POST /v1/owner/gates/{gateId}/devices`, single use, `gate.device_enrol_hours` 24, stored hashed, shown once); the tablet calls `POST /v1/auth/guard/devices/enrol` {code, name} and receives a **device secret** (32 bytes, stored as sha256, shown once). Revoke (`…/devices/{id}/actions/revoke`) ends every open shift on it and revokes their sessions at once.
- **Guards** `smart.gate_guard` per property: display name + PIN (4–6 digits, argon2id); a credential-less `core.user_account` and a `core.membership` role **`guard`** are created with it (guards cannot sign in anywhere else; the role is not invitable). Owner `/v1/owner/gate-guards` (create, list, patch name, reset PIN, revoke). Lockout after `gate.pin_max_attempts` (5) wrong PINs for `gate.pin_lock_minutes` (15).
- **Sign-in** on an enrolled tablet: `POST /v1/auth/guard/roster` {deviceId, deviceSecret} → active guards of the gate's property (id + name); `POST /v1/auth/guard/sign-in` {deviceId, deviceSecret, guardId, pin} → token pair (aud `guard`, scopes `tenant:`, `property:`, `gate:`, `gate_device:`, `shift:`) and a **shift** `smart.guard_shift` (a guard's open shift elsewhere is closed `superseded`). Refresh (`/v1/auth/refresh`) re-checks shift, device and guard. `POST /v1/guard/shift/actions/end` ends the shift and the session.
- RBAC: role `guard` (tenant, gate only) with `gate.visit.record`; owner-surface permissions `gate.read`, `gate.manage`, `gate.guard.manage`, `gate.log.read` (reason-logged visit log), `gate.invite.approve`. Owner and manager get all; committee `gate.read` + `gate.log.read` + `gate.invite.approve`; staff `gate.read`. `docs/rbac.md` regenerated.

## 2. Visits (D-315, §7.6 J4-d, J4-e)
- `smart.visit`: gate, property, unit (destination, optional for `other`), kind `guest | delivery | contractor | resident_vehicle | other`, state `requested → approved | denied | timed_out → entered → exited` (+ `cancelled`), plate (Thai category letters + number + province), optional visitor name, optional **ID last 4 digits** (exactly 4 digits, `CHECK (id_last4 ~ '^[0-9]{4}$')`, never more), optional photo (a `core.document` kind `other`, retention class **`visitor`**), `entry_basis` (`approval | invite | remembered_vehicle | delivery_drop_point | guard_override | offline | policy`), `client_ref` (tablet uuid, UQ per gate), `respond_by`, `timeout_action`, decided by / at, entered / exited at, `overstay_notified_at`.
- `smart.visit_event` (append-only, id = the domain event id so `Last-Event-ID` resumes the gate stream): created, notified, answered, policy_applied, entered, exited, cancelled, photo_added, overstayed, note; actor kind guard / resident / operator / system.
- Guard `POST /v1/guard/visits` (Idempotency-Key + `clientRef`; a replay with the same `clientRef` returns the existing visit, never a duplicate): checks the estate **blacklist** (→ `denied` at once, reason `blacklisted`), a valid **remembered vehicle** of the unit (→ `entered`, notify-only), the **delivery drop point** (property setting `gate.delivery_drop_point` or the house policy override → `entered`, notify-only); otherwise `requested` with `respond_by = now + house timeout` and every resident of the unit notified. Offline visits (`recordedAt`, `enteredOffline`) are stored as recorded (entered at `recordedAt`, ≤ `gate.offline_max_hours` 24 old).
- Guard actions: `enter` (from approved / timed_out with allow_and_log or guard_calls; from requested only with a reason = guard override, D-315 "never force every visit to wait"), `exit`, `cancel`, `photo` (inline JPEG/PNG ≤ 2 MB), list (queue / inside / today), get, `GET /v1/guard/units?q=` (unit picker with "LINE linked" flag, never names of residents beyond the first name), `GET /v1/guard/privacy-notice`.
- **Residents** (unit roles `co_owner | tenant | co_tenant | family` from JR — payer-only gets nothing): notified through event `gate.visit.requested` → LINE Flex with approve / deny / call-me buttons into the LIFF (urgent: ignores quiet hours) + in-app; `GET /v1/resident/visits` (my units only), `GET …/{visitId}`, `POST …/{visitId}/actions/approve|deny|call-me|exit`. **First answer wins**: a conditional update on `state = 'requested'` under a row lock; a later answer returns the visit with `accepted: false` and who answered (others see the result); the same resident repeating the same answer is idempotent. Approve may `rememberVehicle` (30 days).
- **House policy** `smart.house_gate_policy` per unit: timeout seconds (default property setting `gate.policy.timeout_seconds` 180, 60–900) and action `allow_and_log | deny | guard_calls` (default `gate.policy.action` `guard_calls`), `delivery_skip_approval` (null = estate setting), household note. Owner `GET|PUT /v1/owner/gates/unit-policies/{unitId}`; resident `GET|PUT /v1/resident/units/{unitId}/gate-policy` (co_owner, tenant, co_tenant).
- **Timeouts**: job **`gate-visits`** (every 15 s) moves `requested` visits past `respond_by` to `timed_out` with the policy's action (event `gate.visit.timed_out`) and alerts open visits older than `gate.open_visit_alert_hours` (24) once to owner / manager / committee (`gate.visit.overstayed`). D-327: a 3-minute clock lives on the visit row + this sweep, not on a workflow instance (visits are purged at 90 days; the engine's SLA units are hours / days).

## 3. Invites, remembered vehicles, blacklist (§7.6 J4-f, J4-g, J4-h)
- Resident `POST /v1/resident/units/{unitId}/visit-invites` {usage single|multi, visitorKind, validFrom, validTo (window ≤ `gate.invite_max_days` 30), maxUses (multi 2–100), plate?, visitorName?} → QR token `gpv1.<base64url>` returned once (sha256 at rest). Contractor invites start `pending_approval`, the owner approves / rejects (`gate.invite.approve`). List / revoke. Guard `POST /v1/guard/invites/actions/scan` {token, clientRef, plate?} → visit `entered` at once (uses counted atomically; plate checked when the invite names one; another estate's invite = 404).
- `smart.remembered_vehicle` per unit (kind resident | visitor, expires after `gate.remember_days` 30): from an approval with `rememberVehicle`, or resident `POST|GET|DELETE /v1/resident/units/{unitId}/remembered-vehicles`. Entry becomes notify-only.
- `smart.gate_blacklist` per property: plate + reason (required, audited), revoke with reason. Owner `GET|POST /v1/owner/gates/blacklist`, `…/{id}/actions/revoke`.

## 4. PDPA, retention, arrears, logs
- Purpose / consent text from setting `gate.privacy_notice` (th / en, version; draft ⚖) on the guard surface and in the resident gate view.
- Job **`gate-retention`** (daily): per tenant `gate.retention_days` (90, tenant may lower, 1–90) — **deletes** visits (events cascade), their photos (object + derivatives deleted, `core.document` row deleted), invites ended before the cutoff, expired / revoked remembered vehicles, revoked blacklist entries; one audit row per tenant with counts only. Domain-event payloads and audit rows of the gate carry ids only (no plate, name, ID digits).
- Residents read only visits of units they hold a role on (404 otherwise). Owner visit log `GET /v1/owner/gates/visits` and `…/{visitId}` need `reason` (5–500 chars) — one audit row `gate.visit_log_read` per read.
- `gate.show_arrears` (false, ⚖ O-038, platform compliance admin): while false no arrears field exists in any guard response; when true the unit picker shows only `hasArrears` (boolean).

## 5. Realtime
- `GET /v1/guard/events` (SSE, Bearer guard token): replays the gate's visit events after `Last-Event-ID` (header or `lastEventId` query, last 24 h, ≤ 500), then streams live messages of channel `gate:<gateId>` with `id:` = visit event id; heartbeat 25 s. `GET /v1/guard/visits/changes?after=` is the JSON twin for clients that cannot stream (and for the offline queue).
