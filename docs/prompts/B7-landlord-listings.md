You are a senior backend engineer on **`getproperty-api`**. Decisions **D-250 – D-263** (all *Proposed*, founder 2026-10-24) rule here, together with D-020–D-025 (statutory values), D-050 (VAT documents), D-062 (e-signature), D-151–D-153 (vocabulary, tenancy, asset core), D-216 (TM30), D-232 (branding). Open items **O-017 – O-019**: the founder chose (2026-10-24) to **ship with Claude's recommended defaults switched on** and let counsel revise the wording later — keep every legal value a setting and every legal text a versioned template so that revision is data, not code.

**Product principle (founder, 2026-10-24): comfort and sincerity for both sides.** Easy, honest, no tricks: no hidden information, no dark patterns, every fee shown before it is paid, every step doable from a phone in LINE. Comfort is the moat — when owners and residents find it easier to stay on getproperty than to close the deal privately, the ecosystem holds without lock-in tactics.

**Who this is for.** People who own a house or a condo unit and rent it out themselves. Today they find tenants on listing sites or through agents (≈ one month's rent per lease), write their own lease, chase rent in chat and check slips by hand. getproperty gives them, free (D-250): a listing that brings enquiries into LINE, a proper lease, automatic rent collection, and every document they need (D-253). Competitive context (Oct 2026): Rentdi (free listing, 4 % of rent collected), Renterday / เช่าเฮงเฮง (free for 1–3 rooms), listing portals without management. We win on: one flow from listing to move-out, bank/gateway-confirmed payments, bilingual leases + TM30 for foreign residents, owner verification, and the annual income summary.

**Schema changes go to `docs/schema-design.md` first (a PR to that file), then migrations.** `core.*` changes (enum values such as `building_type.house`, `document_kind.listing_photo`, `document_kind.inspection_report`, `unit_ownership` source `self_declared`) are made in `collective-asset-core` and released before the app migration (D-153).

## Deliverable 7.1 — Self-serve landlord sign-up and portfolio units (D-251)
1. `POST /v1/public/signup/landlord` with any D-255 identity — **phone OTP, Google or Apple (Firebase ID token verified server-side), LINE Login / LIFF** — the same providers as getpack (`phone_otp | firebase_google | firebase_apple | line`); add the missing providers to `core.user_identity.provider` through an asset-core release, a `FirebaseAuthAdapter` (verify ID token, fake in tests) and identity linking from the profile: creates `core.tenant` (`type = landlord`, status `active`, D-250 free), the person's `core.party` as `legal_party`, the owner membership and role, default settings; idempotent per identity (a second call returns the existing tenant). Rate-limited; abuse signals logged. Company landlords add `legal_form`, tax id and VAT flag later in settings.
2. Unit intake (`POST /v1/owner/portfolio/units`): kinds `condo_unit | house | townhouse | room`. House/townhouse → property + building (`building_type` `house`) with one unit. Condo unit → find-or-create a **stub** property/building by normalised project name + address + geo (`building.status` `external`, owner/operator null) and the landlord's `core.unit_ownership` (`source` `self_declared`); a later juristic tenant on getproperty links the stub through `core.asset_access_grant` (`landlord_unit`) — write the merge procedure and its test now, even if no juristic exists yet. Fields: size m², bedrooms, bathrooms, floor, furnishing, default rent, photos (documents).
3. `GET /v1/owner/portfolio` — the portfolio-first home: per unit occupancy state (vacant / listed / leased / notice given), current lease end, this month's invoice status, open service requests; totals (expected, collected, overdue) as decimal strings. One query plan, ≤ 150 ms p95 for 50 units.
4. `me` returns `tenantType = landlord` and the landlord menu (portfolio, listings, leads, leases, invoices, documents, tax summary, settings). RBAC: owner only by default; optional co-manager invitation (family member) with `landlord.manage`.
5. Acceptance: e2e sign-up by LINE, phone, Google and Apple (fake Firebase) → tenant + party + membership; idempotent replay; house and condo intake; two landlords in the same condo share one stub building and see only their own units (RLS test); stub → real building link test.

## Deliverable 7.6 — Payment gateway with split settlement, verified-slip fees and the fee ledger (D-250)
1. `PaymentGatewayAdapter` port (create Thai QR / card payment intent per invoice, webhook verify, refund, settlement report) with **sub-merchant onboarding** (`platform.payout_account` per operator tenant and building: bank account encrypted per D-148, KYC state mirrored from the provider) and **split settlement** — the platform fee is deducted by the provider at settlement, the rest goes to the operator; Collective never holds resident funds. Provider per O-020; a fake adapter for tests and dev. Existing D-042 QR adapters stay for tenants not yet onboarded.
2. **Flexible fee rules** (D-250 item 1): `platform.payment_fee_rule` + versions (effective-dated, maker-checker publish like tariffs): `percent`, `flat`, `minimum`, `cap`, optional `tiers` by payment amount, `mdr_treatment` (`included` = all-in, the platform pays the gateway MDR from the fee; `passed_through` = MDR added on top), VAT mode, rounding; scoped by `channel` (`gateway_qr | gateway_card | verified_slip | manual`), tenant type and optional tenant override. A pure `computeFee(rule, amount, channel, mdr)` with exhaustive unit tests (decimal.js, no floats); every number a setting, none in code.
3. **Who bears the fee** (item 3): per-building `payment_fee.bearer = owner | resident`; `resident` is allowed now (founder 2026-10-24; `payment_fee.resident_bearer_allowed` defaults to true and stays a platform setting so counsel can narrow it later); the fee is then a separate `invoice_line` (`source_type` `payment_fee`) always shown before payment.
4. **Verified slips** (item 4): a direct transfer becomes a confirmed payment only after the slip-verification adapter (D-043, `ops-payments/slips.service.ts`) verifies it; on confirmation a `fee_ledger` row (`channel` `verified_slip`, bearer always the operator, no split) is written and billed on the operator's **monthly platform fee invoice**. `manual` (cash) payments use the `manual` rule (default 0) and are counted per tenant for monitoring (`platform.analytics_fact`).
5. Fee ledger and billing: `platform.fee_ledger` (payment, channel, gross amount, fee, MDR, VAT, bearer, settled_by `split | invoice`); monthly platform fee invoice per operator tenant for the `invoice`-settled rows (B6.1 platform invoicing, no plan); reconciliation of split rows against the provider's settlement report with discrepancy alerts; admin reports of fee revenue, MDR cost and margin per channel.
6. `GET /v1/public/payment-fee` (web contract request 2026-10-24): the published rules a prospect may see (channel, percent/flat/min/cap, MDR treatment, VAT) — no tenant overrides.
7. Acceptance: `computeFee` table tests (percent, flat, percent+flat, min, cap, tiers, MDR included vs passed through, VAT, rounding); e2e invoice → gateway QR (fake) → webhook → receipt → fee ledger (split); e2e transfer → slip verified (fake) → receipt → fee ledger (invoice) → monthly fee invoice; resident-borne fee shown as its own line before payment; idempotent webhooks; settlement mismatch alert.
