You are a senior backend/IoT engineer on **`getproperty-api`**. Decisions D-012, D-013, D-030–D-035, D-130–D-132, D-142, D-143, D-151, D-157 rule here. A meter is a **`core.asset_item`** (category `meter_electric | meter_water`) bound to a unit or a common area over time by **`core.meter_assignment`**; the hardware behind it is a **`smart.device`**. The billing engine (B4) will read only the **`smart.meter_reading`** table you build in 3.3.

## Deliverable 3.1 — Device registry, provisioning, meter channels, config push, OTA (ADR-0005, 0006)
1. Migrations (schema `smart`): `device` (serial, model, kind `gateway | electric_meter | water_meter | lock | breaker | sensor`, driver, firmware, ownership `platform_haas | tenant_owned`, `tenant_id`/`building_id` null while in platform inventory, `asset_item_id` once installed, state D-033, certificate fingerprint, last_seen, `last_seq`), `device_certificate`, `provisioning_code`, `meter_channel` (meter asset item ↔ gateway bus config with `valid_from/to`: bus/address/pin, register map, scale, litres per pulse), `gateway_config` (version, document jsonb, published_at, applied_at), `meter_swap` (old/new device, closing and opening `meter_assignment`, last old register, first new register, staff, photos), `ota_release`, `ota_rollout`, `ota_rollout_device`, `device_command`, `meter_status`. Breakers are modelled (`kind = breaker`) but **no cut-off command exists** (D-024, D-157).
2. Admin endpoints (`/v1/admin/devices*`): inventory import (CSV of serials/models), assign to tenant/building, fleet views (online/offline/degraded per building), OTA releases & rollouts (rings canary → pilot → all), certificate revoke/retire.
3. Staff endpoints (`/v1/staff/devices*`): provisioning by scanning the gateway QR (`POST .../provision` → provisioning code issued), install a meter device on a meter position (creates/links the `asset_item`, opens the `meter_channel`, and records the **physical register value at install** — photo required; this becomes the first `meter_reading` with `source: manual`, `is_install`), unbind/swap flow (closes the old `meter_assignment` with its final reading, opens the new one with its initial reading, both photos), "identify" command (LED blink).
4. Config compiler: `GatewayConfig` document per gateway from current meter channels (D-131; `roomCode` on the wire = the unit no. or assignment code) → published retained on `gp/v1/<gatewayId>/config` through the mqtt integration (fake in tests) → `config_applied` event updates `config_applied_version`; drift detector job flags gateways whose health reports an older version for > 15 min.
5. Commands: `POST /v1/owner|staff|admin/devices/{id}/commands` (read_now, restart, identify, upload_logs; `ota_apply` admin only), `cmd/ack` consumer, expiry + retries.
6. Acceptance: e2e provision gateway (fake CSR) → install 2 meters with install readings → config v1 published (snapshot test of the document) → health reports v1 → swap one meter → config v2 and two meter assignments with no gap/overlap; tenant A cannot see tenant B's devices (404 + RLS); platform fleet view counts inventory devices with no tenant.

## Deliverable 3.2 — MQTT ingest & telemetry
1. `ingest` process: EMQX shared subscription; validate `TelemetryBatch`/`Health`/`DeviceEvent` against the DTO classes (the same classes export `contract/device-protocol.json`); authorise `(gatewayId, meterId)` against current meter channels; dedup on `(meterId, seq)` per D-143 (Redis bloom → `smart.device.last_seq` watermark → `smart.ingest_seq_mark` window → `meter_reading UQ(device_id, seq)`); write `smart.telemetry_point` (TimescaleDB hypertable, chunk 7 days, compression after 30 days, retention 24 months raw, continuous aggregates `15m/1h/1d` kept 5 years) and `smart.device_health` (hypertable) + `smart.device_health_latest`; `smart.device_event`; emit events `reading.candidate` (per reading with `quality`), `device.online/offline/degraded`, `device.event.*`.
2. HTTPS fallback `POST /v1/device/readings/batch` with the same pipeline; `GET /v1/device/config`; `GET /v1/device/ota/manifest`; `POST /v1/device/logs/presign`.
3. Owner/resident series endpoints: `GET /v1/owner/meters/{assetItemId}/series?from&to&bucket`, `GET /v1/resident/leases/{id}/usage?bucket=1d` (D-063) — from continuous aggregates, never raw billing data.
4. Backpressure: batches > 200 readings rejected with `device.batch_too_large` event; ingest lag metric; dead-letter for invalid payloads with admin replay.
5. Acceptance: integration test with Testcontainers EMQX: publish 1,000 readings across 2 gateways (one duplicates 10 %) → exactly 900 points; a gateway publishing for an unbound meter is rejected and audited; series endpoint returns bucketed usage; health transitions online → offline on LWT.

## Deliverable 3.3 — Meter readings from every source (the billing source of truth)
1. `smart.meter_reading` (asset item, meter assignment, unit (denormalised), device nullable, register `numeric(12,3)`, unit, read_at, source `iot | ocr | manual | estimated`, confidence, quality, evidence `core.document` ref, submitted_by, review state `accepted | pending_review | rejected | corrected`, previous reading ref, consumption since previous, `superseded_by_reading_id` (D-142), `reading_batch_id`); unique `(asset_item_id, read_at, source)`; monotonicity check with overflow handling (rollover at the assignment's `rollover_at` or a swap) — a decreasing register without a swap goes to review. `smart.meter_reading_review`, `smart.reading_batch` (staff round, import, cycle estimate, HTTPS batch).
2. `reading.candidate` subscriber (from 3.2): promote IoT candidates with `quality: good` to accepted readings; `estimated_by_gateway` / `clock_suspect` → accepted with lower confidence and flagged; the billing cut-off selector (B4.2) will prefer the highest-confidence reading inside the window.
3. Staff OCR/manual readings (D-035): `POST /v1/staff/meter-readings` (asset item, photo, optional typed value) → OCR adapter (vision model, fake returns the typed value in tests) → plausibility band vs trailing consumption (setting per utility, default ±60 %) and monotonicity → accepted or `pending_review` with the photo; owner review queue `GET/POST /v1/owner/meter-readings/review*` (accept, correct with reason → superseding row, reject); tenant setting `readings.require_photo`. Move-in/out inspection registers (B2.4) are inserted here as `manual`.
4. Reading rounds: `GET /v1/staff/reading-rounds/current` lists meters (active assignments) that still need a reading before the cut-off (no IoT, or IoT stale), grouped by building and floor, with the last reading and photo thumbnail — the staff PWA's main screen for Lite buildings; each round is a `reading_batch`.
5. Owner views: meter history per unit across swaps (by assignment) with source badges and photos; export CSV.
6. Acceptance: property tests (monotonic series, rollover, swap across two assignments); e2e manual reading accepted / out of band → review → corrected (superseded row kept); IoT candidate promoted; reading round shrinks as readings arrive; cross-tenant 404s + RLS.

## Deliverable 3.4 — Meter health, utility invoices & loss
1. Health rules (D-034) as tenant-overridable settings: `stale_after` per utility, `silent_after`, gateway offline after 5 missed heartbeats; worker job every 5 min computes `smart.meter_status.health` (`ok | stale | silent | no_device`) and emits `meter.stale/silent` → notifications to owner & staff, and `service.auto_request_requested` (consumed in B5; until then logged).
2. `ops.utility_invoice` (D-032): owner enters the MEA/PEA/MWA/PWA invoice per building per period (period, units, amount, photo; OCR adapter prefill), or imports from the utility's e-bill PDF; `ops.loss_report` computed per building per billing cycle after invoices are issued (B4): `invoice_units − Σ unit-billed units − Σ common-area units` in units and THB at the utility tariff, loss %, trend; `ops.loss_suspect`: zero-consumption occupied units, consumption in vacant units, meters with `estimated` readings, night-time water flow (from `15m` aggregates), meters whose consumption changed > 2σ.
3. Endpoints `/v1/owner/buildings/{id}/utility-invoices*`, `/v1/owner/buildings/{id}/loss?cycle=`; dashboard widget data (B6 reads it).
4. Acceptance: golden test of a loss report from a fixture building (12 units, 1 vacant with usage, 1 stale meter); e2e enter invoice → loss report after invoices exist (use B4 fixtures or a stubbed billed-units provider until B4.2 lands — mark in PROGRESS).

After each deliverable: `docs/PROGRESS.md`, both contracts regenerated, commit, and tell `getproperty-edge` when `device-protocol.json` changed.
