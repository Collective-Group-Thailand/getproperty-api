You are a senior backend engineer on **`getproperty-api`**. This prompt builds group A1 (Lease & Occupant) on the neutral asset core that metering (B3) and billing (B4) attach to. Decisions D-010, D-020, D-023, D-025, D-060–D-064, D-151, D-152, D-158 rule here. Vocabulary (D-151): the customer is the **tenant**; the person who rents is a **party** (lessee) living in a **unit**; residents use `getproperty-liff` through `/v1/resident/*`.

## Deliverable 2.1 — Properties, buildings, floors, units, meters on the board
1. Tables already exist in `core` (`property`, `building`, `floor`, `unit`, `asset_item`, `meter_assignment`). Migrate the `ops` side per schema-design v2: `ops.unit_profile` (v1 room types: size, default rent, default deposit months, default lease lines, inspection template), `ops.unit_detail` (per-unit operational data: profile, current lease, status reason), `ops.utility_account` (MEA/PEA/MWA/PWA customer numbers per building), `platform.property_setting_version` if not yet migrated.
2. Endpoints `/v1/owner/properties*`, `/v1/owner/buildings*` (building with `owner_tenant_id = operator_tenant_id = current tenant` for apartments; type, floors), `/v1/owner/buildings/{id}/floors*`, `/v1/owner/units*` (unit no., `type` default `room`, floor, area, `base_rent`, status `vacant | reserved | occupied | maintenance | inactive`, `ownership_ratio` stays null for apartments), bulk unit creation (floor × pattern `A-{floor}{nn}`), Excel import/export of units (template download, validate, preview, commit — the Phase 1 "import from Excel" acceptance), meter positions: one meter `asset_item` per unit and utility (manual meters for Lite buildings) with a `meter_assignment` (initial reading, multiplier), appliances/furniture as `asset_item`s (v1 amenities), unit board data (`GET /v1/owner/buildings/{id}/board` → floors with unit cards: status, lessee name, balance, meter health — later fields null until B3/B4).
3. Unit status transitions are driven by leases (B2.3) and service work (B5); manual override only `vacant ↔ inactive | maintenance` with a reason and audit.
4. Acceptance: e2e create property → building → bulk units → import Excel → board; cross-tenant 404s and RLS tests; a second tenant with an `asset_access_grant` on one unit (landlord case) sees that unit only; unit-count snapshot endpoint for subscriptions (B6) returns units ≠ `inactive` (D-082, D-156).

## Deliverable 2.2 — Parties, occupancy, invitations, LINE linking
1. `core.party` (person / company: names, phone, nationality, language, ID document type and number **encrypted with the tenant's data key**, document files in `core.document` with retention class `id_document`, emergency contact), `core.party_user_link` (party ↔ `core.user_account` / LINE identity), `core.occupancy` (who lives in a unit, `role` `tenant | co_tenant | owner_occupier | family | staff`, from/to), `ops.occupant_profile` (TM30 fields: visa type, arrival date — D-052), `platform.invitation` (`kind = lease_resident`, QR + SMS link, expiry, state). For apartments the tenant's own legal entity is a `party` with one `core.unit_ownership` row per unit (blueprint: the owner of every unit is the tenant itself).
2. Endpoints: owner/staff create party (minimal fields; documents optional until contract signing), invite to a lease (`POST /v1/owner/leases/{id}/invitations` → LINE QR image + SMS), resident accepts (`POST /v1/resident/invitations/{code}/accept` after LINE login + consent D-025), one LINE account across several leases (and tenants), unlink with Owner approval.
3. PDPA: consent capture with purpose versions on first resident login; `GET /v1/resident/me/privacy`, DSR entry points; ID document images and decrypted ID numbers available only to Owner/Manager, every access audited.
4. Acceptance: e2e invite → LINE login (fake) → consent → accept → `/v1/resident/me` lists the lease; document access audited; a party of tenant A cannot be invited to tenant B's lease; the same LINE user linked to parties in two tenants sees both leases.

## Deliverable 2.3 — Leases, standard contract, e-signature, notices
1. `ops.lease_template` (+ versions: platform-provided **สคบ. standard contract** text, th; a tenant may add an addendum within allowed clauses — the compliance engine lists forbidden clause types), `ops.lease` (unit, `lessee_party_id`, term, start/end, rent, deposit, advance rent, billing day, utility billing mode `metered | included`, rate plan references (B4.2, nullable until then), parking, keys, `terms` jsonb; state `draft → pending_signature → active → notice_given → ending → ended | terminated | cancelled`), `ops.lease_party` (lessee, co-tenants, guarantor, occupants), `ops.lease_line` (fixed monthly items with amount and kind), `ops.lease_signature` (signer party/user, method, OTP ref, LINE user id, signed PDF document, sha256, ip, ua), `ops.lease_event`. Activation creates the `core.occupancy` rows (role `tenant` for the lessee) and sets the unit `occupied`.
2. Compliance at lease creation (D-020/D-023, scope ≥ 3 units D-158): deposit + advance ≤ cap setting; forbidden clauses blocked; utility mode `metered` requires rate-plan billing (B4); renewal fee not allowed; mid-term rent increase only if the lease recorded it at signing.
3. Endpoints: owner CRUD drafts, preview contract PDF, send for signature; resident views contract in LIFF, signs (draw-to-sign, OTP, D-062); owner countersigns; activation sets the unit `occupied` and opens the deposit receipt (2.4); **30-day notice** by the resident (`POST /v1/resident/leases/{id}/notice`) or the owner (with legal reason codes); renewal (new lease from old, pre-filled); termination with reason and evidence; lease history; `GET /v1/resident/leases/{id}/contract` (signed PDF).
4. Documents: contract PDF (Puppeteer, Thai fonts, both signatures, hash in footer) stored as `core.document`, number from `ops.document_series` type `contract`.
5. Acceptance: golden test of the contract PDF text for a sample lease; e2e draft → sign (resident) → countersign → active (occupancy created) → notice → ending → ended (occupancy closed); deposit above cap refused with `compliance.deposit_cap` + `legalRef`; forbidden clause refused; overlapping active leases on one unit refused (exclusion constraint).

## Deliverable 2.4 — Deposits, move-in/out inspections, settlement
1. `ops.deposit` (lease, amounts received per type, receipt ref, state `pending → held → settling → refunded | forfeited_partially | disputed`), `ops.deposit_settlement` (opened_at, deadline = move-out + 7 days, inspection refs, final invoice ref (B4), proposed refund, resident response, refund record with transfer evidence, statement number + document, closed_at; driven by a **workflow instance** with the 7-day SLA timer, D-159), `ops.deposit_settlement_item` (damage items with evidence document refs and amounts), `ops.inspection` (type `move_in | move_out | periodic`, checklist per unit profile, items with condition + photos, signatures), `ops.inspection_template`, `ops.inspection_item` (meter registers captured at move-in/out are inserted into `smart.meter_reading` source `manual` once B3.3 exists; until then kept on the item).
2. Flow (D-023): activation → deposit receipt; lease ending → move-out inspection task for staff (B5 queue; here an endpoint) → comparison view move-in vs move-out per item → owner proposes settlement (deductions require a damage item + photo; normal wear category cannot be deducted — rule `compliance.deposit_wear`) → resident accepts or disputes in LIFF → refund recorded (bank transfer reference) → closed. Deadline reminders to the owner at T-3, T-1, overdue (workflow timers); dashboard counter.
3. Endpoints under `/v1/owner/deposits*`, `/v1/staff/inspections*`, `/v1/resident/deposits*`.
4. Acceptance: e2e full flow with a deduction accepted and one disputed; deduction without evidence refused; refund after deadline flagged `late` by the workflow breach, in the audit and the tenant's compliance score (B6 analytics).

After each deliverable: `docs/PROGRESS.md`, contract regenerated, commit.
