You are a senior backend engineer on **`getproperty-api`**. Decisions D-020–D-025 (incl. D-021a), D-030–D-032, D-040–D-046, D-050–D-051, D-140, D-141, D-146, D-151, D-158 rule here. Vocabulary (D-151): a bill is an **`ops.invoice`** with **`ops.invoice_line`** rows whose `source_type` (rent / meter / common_fee / fund / penalty / service / deposit / adjustment) says where the amount came from; the payer is a **party** (`billed_party_id`), not a user; formulas are **data** (`ops.rate_plan_version.tiers` jsonb) interpreted by one engine — the same engine will later compute condo common fees by `ownership_ratio` (do not hard-code apartment assumptions).

## Deliverable 4.1 — Compliance engine (ADR-0007)
1. `core/compliance` module: a rule registry where each rule has `id` (`compliance.tariff_cap` (severity `warn` by default, D-021a), `compliance.bill_disclosure`, `compliance.invoice_lead_time`, `compliance.water_minimum` (D-141), `compliance.deposit_cap`, `compliance.deposit_wear`, `compliance.deposit_deadline`, `compliance.no_renewal_fee`, `compliance.no_midterm_increase`, `compliance.notice_period`, `compliance.no_cutoff` (D-024, D-157), `compliance.late_fee_policy` ⚖), `legalRef` (clause ids of `docs/compliance/legal-reference.md`, D-149), `severity` (`block | warn`, overridable platform-wide or per tenant by the platform admin), `appliesTo` (lease, rate_plan, invoice, deposit, access), an `evaluate(context)` function and a unit test proving pass, warning and refusal. Rules read thresholds from settings (effective-dated). Rules apply to tenants in scope (`tenant.subject_to_ocpb_2568`, ≥ 3 units, D-158).
2. `ComplianceError` → problem `422` with `code`, `legalRef`, `detail` th/en; warnings → `409 compliance.acknowledgement_required` with the warning text and values; acknowledgement → `platform.compliance_acknowledgement` (who, when, IP, rate and cap shown) and the request is repeated with its id; `@ApiCompliance()` lists the rules an operation can raise; every evaluation that warns or blocks is a `platform.compliance_evaluation` row.
3. Tenant **compliance score** materialised per month (`platform.compliance_score`: invoices within the utility rate, lines above cap acknowledged, deposits refunded on time, contracts on the standard template) — used by B6 analytics and shown on the owner dashboard.
4. ADR-0007 (rule engine) and ADR-0008 (payment adapters, no funds held).
5. Acceptance: every rule has tests; `pnpm compliance:report` prints the rule table (id, legalRef, severity, covered operations) into `docs/compliance.md`.

## Deliverable 4.2 — Rate plans, billing cycles & invoices
1. Migrations: `ops.rate_plan` (tenant, building nullable = tenant-wide, kind `power | water | common_fee | rent | service`, name) + `ops.rate_plan_version` (effective_from, `tiers` jsonb shape per schema-design v2 §4.2.2, minimum charge (D-141), basis `per_unit | per_sqm | per_ownership_ratio | fixed`, cap check snapshot, `above_cap`, acknowledgement ref); `ops.billing_cycle` (property, period, cut_off_at, state `open → readings_pending → computed → issued → closed`, stats), `ops.invoice` (tenant, building, unit, **`billed_party_id`**, lease nullable, cycle, number from series, period, due date, status `draft → issued → partially_paid → paid | overdue | void`, totals, `has_above_cap_line`, snapshot jsonb: utility tariff versions, rate plan versions, readings used, lease lines, settings; immutable after issue — append-only trigger), `ops.invoice_line` (`source_type` enum + `line_kind` enum (D-041 detail), `source_id`, description, quantity `numeric(12,3)`, unit, unit price `numeric(14,4)`, amount, meter asset item / assignment, from/to reading refs → `smart.meter_reading`, utility tariff version, rate plan version, `cap_per_unit` (effective average rate, D-140), `above_cap`, acknowledgement ref, compliance flags), `ops.invoice_line_kind_rule`, `ops.credit_note` / `ops.debit_note` (+ lines; reference invoice, reason), `ops.estimate_settlement`.
2. Rate plan maintenance (owner): create/edit versions (future-dated allowed, backdating refused); saving a power/water version whose rate exceeds the utility's effective average rate for a representative consumption shows the D-021a warning and requires acknowledgement (or refuses where severity = `block`).
3. Cycle job (D-031): at cut-off per property → for each active lease (and, later, each billable ownership for condo tenants — keep the loop on `billed_party` × unit, not on lease only): select readings per meter assignment (highest confidence inside the window; else request a reading → reading round; after the grace deadline apply the tenant's `estimate_policy`) → compute lines: rent (pro-rata by calendar days for partial months), lease lines, power and water units × **rate plan version** in force (tiers interpreted by the engine), each meter line compared with the **utility tariff** effective average rate for that consumption (D-021a/D-140: `above_cap` flagged, acknowledgement required or blocked per severity), common fees, one-offs queued for the period, prior balance carry-over, estimate settlement from the previous cycle → invoice draft with totals (D-046 rounding).
4. Owner review: `GET /v1/owner/billing-cycles/{id}` (per-unit table: readings, units, amount, flags incl. above-cap), edit one-offs, re-compute, **issue** (`POST .../actions/issue`, idempotent) → invoices become immutable, numbered (4.3), event `invoice.issued` → LINE Flex + PDF (4.3) → resident. Auto-issue setting (`billing.auto_issue` after N hours without owner action, default off).
5. Corrections: void an invoice before any payment (new invoice in the same period), or credit/debit note after; both re-open the receivable balance (4.5).
6. Resident endpoints: `GET /v1/resident/invoices`, `/invoices/{id}` (lines with readings and photos where they exist, D-022), `/invoices/by-number/{n}`.
7. Acceptance: **golden tests** — fixtures for: full month, move-in mid-month, move-out mid-month, MEA tiered utility tariff vs flat tenant rate, rate above the effective average rate warned + acknowledged (and refused under `block`), water minimum charge (D-141), estimate then settlement, prior balance, credit note, swap within the period (two assignments); property tests: Σ lines = total, rounding stable; e2e cycle → readings pending → staff reading → computed → issued → resident sees it → void → re-issue.

2. LINE Flex message builders for invoice, receipt, reminder, deposit statement (bubble carousel for multi-unit residents).
3. Endpoints: owner list/download/resend; resident download; admin template preview; document archive export (zip per period).
4. Acceptance: snapshot tests of PDF text per document type; number series gapless under concurrent issue (integration test with 50 parallel issues); Flex JSON validated against LINE's schema.

## Deliverable 4.4 — Payments: Thai QR per invoice, webhooks, slips, receipts, tax invoices
1. `QrPaymentAdapter` interface (create dynamic QR for amount + reference, query status, parse webhook, settlement file) with providers behind feature flags (KBank API, SCB, Opn — O-001; fake in tests) configured **per tenant** with the tenant's own merchant/bank account (`platform.tenant_bank_account`, D-042). `ops.payment` (invoice, payer party, amount, method `qr | transfer_slip | cash | bank_transfer_manual | offset`, provider ref, state `pending → confirmed | failed | refunded | reversed`, confirmed_at, slip document, reconciled_at), `ops.payment_allocation` (payment → invoices, for multi-invoice payments), `ops.payment_qr_code`, `ops.slip_review`, `ops.payment_settlement_file`, `ops.receipt` (kind `payment | deposit | advance`), `ops.tax_invoice` (`tax_invoice | receipt_tax_invoice`, O-004).
2. Flow: invoice issued → QR created (reference = invoice number, `promptpay_ref`) → embedded in PDF/Flex → `POST /webhooks/payments/{provider}` (signature verified, idempotent on provider ref) → payment confirmed → allocation → invoice `paid`/`partially_paid` (tenant setting `payments.allow_partial`) → event `invoice.paid` → receipt issued (4.3) and sent. Daily settlement reconcile job catches missed webhooks and flags discrepancies to the owner.
3. Slip fallback (D-043): `POST /v1/resident/invoices/{id}/slips` (image) → slip-verify adapter → match amount + tenant account + not previously used → auto-confirm; else owner review queue (`/v1/owner/slip-reviews*`) with approve/reject and duplicate warnings. Owner manual record for cash/transfer with evidence (audited).
4. Refunds and overpayment: credit to the payer's balance by default; refund record with transfer evidence; receipts for overpayments as advance receipts.
5. Acceptance: e2e QR webhook → paid → receipt; duplicate webhook ignored; partial payments; slip verified auto; forged/duplicate slip → review; settlement file with a missing webhook creates the payment; tenant B's webhook reference cannot pay tenant A's invoice.

## Deliverable 4.5 — Receivables, dunning (light), penalties, exports
1. `ops.receivable_entry` ⟲ / `ops.receivable_balance` (per billed party × unit — not per lease, so condo co-owners fit later: open invoices, credits, balance, aging buckets); arrears list endpoint with filters and totals; dashboard numbers (`/v1/owner/dashboard` first version: income this month, collected %, arrears, due today, cycle state, compliance score incl. above-cap lines, loss % from B3.4).
2. Reminders (D-045, blueprint A2.5 "dunning เบา"): a **workflow instance** per overdue invoice with the schedule setting (`1,3,7` days after due) as timers; LINE Flex reminder with QR, quiet hours respected, stop when paid, owner-triggered "send reminder now" (`ops.dunning_reminder` log); penalty line (`source_type = penalty`) only when `late_fee.enabled` and `compliance.late_fee_policy` allows (⚖ O-002) — `ops.penalty_assessment` added to the next cycle's invoice, never to the issued invoice. Nothing else automatic (D-024).
3. Exports: Excel (invoices, payments, arrears per period), **FlowAccount** and **PEAK** import formats (sales documents + receipts), VAT output working figures for VAT-registered tenants (ภ.พ.30 figures per month), income/expense summary per building (expenses = utility invoices + work-order costs from B5 when present).
4. Acceptance: e2e overdue → reminder sent on schedule → paid → stops; export files open in the target format (golden CSV/XLSX snapshots); aging buckets correct on fixtures.
