# ADR-0009 — Platform blueprint: tenant types, neutral asset core, schemas

**Status:** Accepted (2026-10-17, schema lock before B1.2 migrations)
**Decision ids:** D-150, D-151, D-152, D-153, D-154, D-156, D-157, D-158, D-159, D-160, D-161 (supersede the naming in D-004 / D-010 and schema-design v1) · `docs/platform-blueprint.md` §"Platform core & collective-asset-core", §"Data model & naming guideline" · amends ADR-0001, ADR-0003, ADR-0004

## Context
getproperty started (B1.1, 2026-10-16) as a SaaS for apartment owners: the customer was an `org`, the person who rents was a `tenant`, a building was a `property` with `rooms`, meters were `meter_points`, bills were `bills`. On the same day the founder adopted the **platform blueprint**: getproperty is Collective Group's *Building Operations* platform for four customer types — apartment owners (the first customer), condominium juristic persons, property-management (PM) companies and small landlords — and shares an asset core (building → unit → party) with **getbuild**, which hands over finished buildings, units, owners and asset lists to getproperty through integration events.

With v1 names, the second customer type would need a migration of every table: a condo has *co-owners* and *common fees* but no "tenants" and no "rent"; a PM company *operates* buildings it does not own; a landlord owns *units* scattered over buildings someone else operates. And "tenant" meaning both "the SaaS customer" and "the person who rents" is the classic multi-tenancy bug. No migration had been applied anywhere and no consumer had generated types from the contract, so the rename is cheap now and expensive later.

## Decision
1. **Tenant = the paying customer organisation** (`core.tenant`, `type` enum `apartment | condo_juristic | pm_company | landlord`, default `apartment`, plus `plan`). Every row carries `tenant_id`; nothing else is called "tenant".
2. **People are parties.** `core.party` (person / company) is the one table for lessees, co-owners, co-occupants, technicians, guarantors and the tenant's own legal entity. Relationships carry the meaning: `core.unit_ownership` (who owns a unit, `share_pct`), `core.occupancy` (who actually lives there, `role` incl. `tenant` = lessee), `ops.lease.lessee_party_id`, `ops.invoice.billed_party_id`. A `core.user_account` (a login) is not a party; `core.party_user_link` connects them.
3. **Neutral asset hierarchy** `property` (group of buildings managed together) → `building` (`owner_tenant_id`, `operator_tenant_id`, `registration_no`, `handed_over_at`, `source_ref`) → `floor` → `unit` (`type` room / condo_unit / house / shop / parking, `area_sqm`, `ownership_ratio` nullable, `status`, `base_rent` nullable). Meters, gateways, locks, pumps, lifts and appliances are `core.asset_item`; a meter is bound to a unit or a common area over time by `core.meter_assignment`. Documents are `core.document`.
4. **Owner vs operator.** A building has an owner tenant (who owns it / the juristic person) and an operator tenant (who runs it now). They are the same tenant for an apartment, different for a condo run by a PM company, and the owner is empty during a developer's post-sale period. An operator change is an update of `operator_tenant_id` (history in `core.building_operator_period`) plus grant changes — data is never copied.
5. **Cross-tenant access only through `core.asset_access_grant`** (grantee tenant, building or unit scope, modules, read/write, validity) — landlords see their units in buildings they do not operate, a PM company sees the buildings it manages, a developer keeps a warranty grant.
6. **One database, six schemas** (D-152): `core` (asset core, tenancy, identity, party — owned by `collective-asset-core`, ADR-0010), `platform` (settings, utility tariffs, identity sessions/roles, subscriptions, audit, events, notifications, files, consents, compliance), `ops` (group A: leases, billing, payments, service, community, workflow), `smart` (group C: devices, telemetry, meter readings, access, energy), `bridge` (`integration_event`, later D1/D2), `juristic` (group B, empty until Phase 2/3). Group B–D tables are not created now; the design only keeps their doors open.
7. **Table conventions** (blueprint rules 1–7): singular snake_case table names qualified by schema; `id uuid` primary keys generated as uuidv7 (no separate public id); `tenant_id`, `created_at`, `updated_at`, `created_by` on every table, `deleted_at` where soft delete applies; statuses and `tenant.type`, `unit.type`, `invoice_line.source_type` are PostgreSQL enums; money `numeric(14,2)` THB, meter quantities `numeric(12,3)`; PII encrypted per column with a **per-tenant data key**; resident features LIFF-first; billing formulas are data (`ops.rate_plan_version.tiers` jsonb) interpreted by one engine.
8. **Row-level security is enforced for the application**, not only for reporting: the app connects as a non-owner role, every transaction sets `app.tenant_id`, and every tenant table has a policy on `core.current_tenant_id()` widened by owner/operator and grant checks for building-scoped rows. Repository filters stay as the first line (cross-tenant id → 404).
9. **API vocabulary follows** (ADR-0003 amended): audiences `operator`, `resident`, `technician`, `platform`, `device`; surfaces `/v1/owner`, `/v1/staff`, `/v1/resident`, `/v1/technician`, `/v1/admin`, `/v1/device`; `X-Tenant-Id`, `tenant:<uuid>` scopes; `TenantContext`.
10. **Nothing the first customer gets changes** (D-150): R1/R2 order of the prompt pack stays; group A for one apartment, on the neutral schema. Compliance rules (D-020–D-025, D-021a, D-140–D-149, D-158) carry over unchanged in meaning.

## Alternatives considered
- **Keep v1 names, add `tenant.type` later:** every later tenant type would need table renames and data moves across billing history; rejected by the founder (D-151).
- **Schema per tenant / database per tenant:** strong isolation, but PM companies and landlords need cross-tenant views of the same building, and getbuild hand-overs move buildings between tenants; shared tables + RLS + grants model that directly.
- **Separate `owner`/`resident`/`customer` tables per role:** one person is often owner, resident and technician at once (blueprint naming guideline); one `party` with relationships avoids duplicates and PDPA requests spanning tables.
- **Bigint identity + public uuid (v1):** cheaper indexes, but ids must travel between getproperty, getbuild and getpack in integration events and be generated in code before insert; uuidv7 keeps index locality and removes the dual-id mapping.
- **RLS only for the reporting role (v1):** one missing `WHERE tenant_id` in a hand-written query would leak; with cross-tenant grants the predicate is no longer a simple equality that every developer gets right, so the database enforces it.

## Consequences
- `docs/schema-design.md` is rewritten as **v2** (same structure as v1, plus a v1 → v2 rename map); B1.2 step 2 writes migrations from v2 only. The unreviewed v1 SQL migrations under `prisma/migrations/` must not be applied (see PROGRESS).
- The `core` schema is owned by the separate package `collective-asset-core` (ADR-0010); getproperty-api installs it and runs its migrations first.
- Prisma uses `multiSchema` (`@@schema("ops")` …); hypertables, RLS, triggers and exclusion constraints stay in raw SQL tails.
- RLS on every query costs a function call per statement (`core.accessible_building_ids()` evaluated once per statement as an InitPlan); B1.2 step 2 benchmarks it on the 300-unit fixture.
- The prompt pack, contract conventions, CLAUDE.md and the legal reference use the new vocabulary; the device protocol is unchanged (its `roomCode` field keeps its wire name until a coordinated edge release).
